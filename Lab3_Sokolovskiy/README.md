# Лабораторная работа №3. Метрики Холстеда

Консольная программа на Java (вариант №2), которая по метрикам Холстеда оценивает число ошибок в ПО и рейтинг программиста.

## Идея

Любая программа состоит из **операторов** (действия: `+`, `if`, вызов функции) и **операндов** (данные: переменные, константы). Из этого считается:

- **N** – длина программы, сколько всего операторов и операндов написано;
- **n** – размер словаря, сколько различных;
- **V = N·log₂n** – объём в битах, то есть сколько информации нужно, чтобы записать программу.

Эмпирический закон: **число ошибок ≈ V / 3000**. Чем больше программа, тем больше ошибок. Всё остальное в лабе – способы оценить V или то, что из него следует.

## Задание 1. Ошибки через «идеальную» программу

Оцениваем минимальный объём ПО боевой космической станции (БКС).

1. **n₂\*** – минимальное число операндов, то есть все входные и выходные данные.
   Входы: 25 целей × 8 параметров × 28 измерений = 5600. Выходы: 25 целей × 3 = 75. Итого 5675.
2. **V\* = (n₂\*+2)·log₂(n₂\*+2)** – потенциальный объём: объём идеальной программы, записанной одним вызовом функции с n₂\* параметрами (+2 – имя функции и скобки). Это нижняя граница.
3. **λ** – уровень языка: чем он выше, тем компактнее код. Реальный объём V = V\*²/λ.
4. Подставляем в «ошибки = V/3000» и получаем **B = V\*²/(3000·λ)** ≈ 1,04·10⁶.

## Задание 2. Ошибки через структуру проекта

Объём считается через модули.

1. **k = n₂\*/8** – правило Холстеда: модуль принимает около 8 входных параметров. Получается ≈ 709 модулей.
2. Столько модулей не потянет один уровень, нужны модули-координаторы. Это иерархия: **i = log₂(n₂\*)/3 + 1 ≈ 5** уровней, число модулей уточняется: **K = n₂\*/8 + n₂\*/64 ≈ 798**.
3. **N = 220K + K·log₂K** – длина программы (220 – среднее число элементов в модуле, K·log₂K – связи между модулями).
4. **V = K·220·log₂48** – объём (48 – размер словаря модуля).
5. **P = 3N/8** – число команд ассемблера.
6. **T_к = 3N/(8·m·ν)** – календарное время: P команд делит бригада из m человек, каждый отлаживает ν команд в день. ≈ 343 дня.
7. **B = V/3000** ≈ 327.
8. **t_н = T_к/(2·ln B)** – начальная надёжность (время наработки на отказ), T_к переводится в часы по длине рабочего дня. ≈ 237 ч.

### Почему B в заданиях 1 и 2 разное

В обоих случаях B = V/3000, но V оценивается по-разному:

- задание 1: V = V\*²/λ ≈ 3·10⁹ бит – оценка «от данных и языка», квадратичная, поэтому раздувается;
- задание 2: V ≈ 10⁶ бит – оценка «от структуры проекта».

Разница на три порядка даёт 10⁶ и 327 ошибок. Это не ошибка расчёта, а результат двух разных методов.

## Задание 3. Рейтинг программиста

У каждого программиста есть рейтинг R, от него зависит, сколько ошибок от него ждут.

- **c(λ, R)** – ожидаемая плотность ошибок (ошибок на Кбайт). Чем выше язык и рейтинг, тем меньше.
- **ΣB/c** – объём, на который программист «должен был» ошибиться при такой плотности.
- **ΣV** – сколько он реально написал.
- Рейтинг растёт, если ΣV > ΣB/c (ошибок меньше ожидаемого), и падает в обратном случае:
  **R₁ = R₀·[1 + 10⁻³·(ΣV − ΣB/c)]**.
- **B = c(λ, R₁)·V_след** – прогноз числа ошибок в следующей программе.

Задание требует проверить три варианта c:

| Вариант c | c(λ, R₀) | R₁ | Ожидаемое B (14 Кбайт) |
|---|---|---|---|
| 1/(λ+R) | 0,000500 | −25 978,40 | −0,00054 |
| 1/(λ·R) | 0,000313 | −42 756,00 | −0,00020 |
| 1/λ + 1/R | 0,625500 | 2021,62 | 8,757 |

Первые два варианта дают c ≈ 0,0005 («ошибок быть не должно»), любая ошибка обваливает рейтинг в минус, и модель теряет смысл. Третий даёт адекватный результат: рейтинг 2000 → ≈ 2022, прогноз ≈ 8,76 ошибки на 14 Кбайт.

Рейтинг пересчитывается за один шаг, c вычисляется при начальном рейтинге R₀.

## Структура кода

Пакет `org.urfu`:

| Файл | Что делает |
|---|---|
| `Main.java` | Точка входа: цикл с меню (1, 2, 3 – задание, 0 – выход) |
| `Input.java` | Чтение числа из консоли; Enter подтверждает значение по умолчанию (вариант №2), запятая и точка допустимы |
| `Task1.java` | Задание 1: n₂\*, V\*, B. Здесь же `log2(x)`, которым пользуются остальные классы |
| `Task2.java` | Задание 2: k, i, K, N, V, P, T_к, B, t_н. Если k ≤ 8, иерархия не нужна и K = k |
| `Task3.java` | Задание 3: метод `c(λ, R, variant)` выбирает один из трёх вариантов коэффициента, `run` считает штраф, R₁ и B для каждого варианта |

Как это работает:

- Каждое задание – отдельный класс с методом `run(Scanner)`: читает параметры через `Input`, считает по формулам, печатает результат. Состояния между запусками нет.
- Значения по умолчанию в `Input` – данные варианта №2, поэтому проверка делается нажатием Enter на все вопросы.
- В `Task3` цикл по `variant = 1..3` один и тот же, меняется только формула в `c(...)`, поэтому три варианта считаются одним кодом.
- Штраф суммируется только по программам с ошибками (`B[k] > 0`).

## Запуск

Нужен JDK 25 (точка входа записана как `static void main()`).

```
mvn compile
java -cp target/classes org.urfu.Main
```

Либо запустить `Main` из IntelliJ IDEA.
